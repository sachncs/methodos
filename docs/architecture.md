# Architecture

`methodos` is a self-evolving procedural graph adapter for LLM agents.
It wraps any `Solver` (host agent decision function) with on-demand
procedural guidance generated by an LLM from a localized subgraph. The
graph itself can be edited offline by an LLM refiner using execution
feedback.

## Modules

```
methodos/
├── schema.py        Pydantic v2 data models + Edit discriminated union
├── graph.py         Pure functions: match, neighborhood, validate, apply_edits
├── llm.py           LLMClient Protocol + LiteLLMClient (litellm)
├── guidance.py      Ψ prompt + generate_guidance
├── adapter.py       AgentState, Solver Protocol, GuidanceCache, PGAdapter
├── evolution.py     Algorithm 1 (refiner + rollback) + EvolutionEngine
├── repo.py          Repository + VectorIndex Protocols, Filesystem + SQLite + SqliteVec
├── service.py       FastAPI app factory (REST: /v1/graphs, /guidance, /evolve)
└── cli.py           Typer CLI (init, inspect, serve, replay, evolve, eval)
```

## Data Flow

### Online inference (per agent step)

```
                    ┌──────────────────────────┐
                    │       Host agent          │
                    │   (any Solver Protocol)   │
                    └────────────▲─────────────┘
                                 │ Action
            ┌────────────────────┴────────────────────┐
            │                                           │
   1. match last action via match_node()               │
            │                                           │
   2. extract h-hop neighborhood (full graph fallback) │
            │                                           │
   3. cache key (graph.id, last_action, last_obs)      │
            │                                           │
   4. guidance = LLM(Ψ_prompt, subgraph) [cached]    │
            │                                           │
   5. state = AgentState(context="### GUIDANCE\n…")    │
            └────────────► solver.step(state)            │
```

### Offline self-evolution (paper Algorithm 1)

```
   for round k in 1..K:
     1. Diagnostic rollout: run_rollout(graph, solver, llm, train_tasks)
         → trajectories + scores
     2. Refiner: LLM(REFINER_prompt, graph, trajectories, rejection_history)
         → list[Edit]
     3. Validate: apply_edits → graph_validate(candidate)
     4. If valid AND val_score ≥ current_score: accept, save
        Else: append to rejection_memory (bounded FIFO)
```

## Protocols (duck-typed, no ABCs)

| Protocol | Methods | Implementations |
|---|---|---|
| `Solver` | `async step(state) -> str` | host agent |
| `LLMClient` | `async complete(system, user, json_schema, temperature) -> str` | `LiteLLMClient` (litellm) |
| `Repository` | `load_graph`, `save_graph`, `snapshot`, `append_trajectory`, `read_trajectories` | `FilesystemRepository`, `SQLiteRepository`, `InMemoryRepository` (test) |
| `VectorIndex` | `upsert`, `query` | `NoOpVectorIndex`, `SqliteVecIndex` |

## Data Model (Pydantic v2)

```python
class ProceduralGraph:
    id: str
    schema_version: Literal[1] = 1
    nodes: dict[str, Node]  # id → Node
    edges: list[Edge]  # (src, dst, relation, attribute)
    terminal_ids: set[str]  # nodes with no outgoing edges (or declared)
    metadata: dict[str, Any]


class Edge:
    src: str
    dst: str  # != src
    relation: Relation  # leads_to | requires | replaces
    attribute: Attribute  # condition, guidance, pitfalls


Edit = EditAddNode | EditDeleteNode | EditAddEdge | EditDeleteEdge | EditUpdateAttr
```

## Persistence

Default: SQLite with WAL + FK + indices (WAL allows concurrent reads
during evolution's rollout phase).

```sql
CREATE TABLE graphs (id PK, schema_version, body, updated_at);
CREATE TABLE trajectories (id PK, graph_id FK CASCADE, split, score, body, ts);
  idx_trajectories_graph_split_ts;
CREATE TABLE snapshots (graph_id FK, tag, body, ts, PK(graph_id, tag));
CREATE TABLE rejection_memory (id PK, graph_id FK CASCADE, body, val_score, ts);
  idx_rejection_graph_ts;
```

Vector search opt-in: `PGRAPH_VEC=1` loads sqlite-vec; `match_node` falls
back to vector similarity when exact-string match fails.

## Caching

`GuidanceCache` is an LRU keyed by `(graph.id, last_action, last_obs)`.
The cache key uses `graph.id` rather than content because content
identity is implicit in id per the contract: graphs evolve by creating
new ids via `apply_edits`.

## Threading model

All I/O is `async def`; concurrency is `asyncio` only. No threading.
SQLite is accessed via `aiosqlite`; the filesystem via `aiofiles`.

## Deployment

- Single Docker container; non-root; `VOLUME /data` for `PGRAPH_HOME`.
- Health endpoint at `/health`.
- Evolution is intentionally NOT exposed as an HTTP endpoint — it requires
  a host Solver which is application-specific.
- Observability is opt-in: `otel-collector` and `prometheus` profiles in
  `docker/compose.yml`.

## What methodos is NOT

- Not a planner / re-planner. The graph is the procedural knowledge; the
  solver retains full reasoning freedom over action selection.
- Not a vector store. Vector search is opt-in and only used for fuzzy Match
  when exact-string fails.
- Not a prompt engine. `Ψ` is a fixed prompt with strict output contract.
- Not a tool-use schema validator. The host agent owns tool schemas.

## Failure modes and recovery

| Failure | Detection | Recovery |
|---|---|---|
| Solver exception | propagates as 5xx in service, RuntimeError in SDK | Host catches; no PG state changes |
| LLM error (transient) | `LLMError` after retries | Caller retries; cache key stable |
| Refiner invalid JSON | logged, returns empty list | Engine rejects; no state change |
| Refiner duplicate edit | `apply_edits` raises | Candidate rejected; added to rejection memory |
| Graph becomes invalid (cycle, unreachable) | `validate()` returns issues | Candidate rejected |
| SQLite WAL corruption | connection raises | Caller retries; data intact |
